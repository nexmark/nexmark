# NexmarkQ3Job.java


This is an **experiment variant** of Nexmark Query 3. The usual Q3 auction
category and Person `state`filters are removed so every
Auction reaches the join. Bid
events are generated by the source but do not enter the join. Join results go
to a discarding sink.
## How the job works

```text
NexmarkSource (Person, Auction, Bid as RowData)
    ├── Person filter/map ── key by Person.id ──────┐
    └── Auction filter/map ─ key by Auction.seller ─┤
                                                    Q3JoinFunction
                                                    │
                                                    DiscardingSink
```

1. **Build phase (`--phase build`):** Person events populate `personState`.
   Take a savepoint after the state has reached the intended size. To build
   Person-only state with an exact count, set `--person-proportion 1`,
   `--auction-proportion 0`, `--bid-proportion 0`, a finite `--events` count,
   and `--source-keep-alive true`. The source then stays running after it
   emits all requested events, allowing stop-with-savepoint.
2. **Measure phase (`--phase measure`):** Restore that savepoint. The Person
   filter drops all new Person events, so the restored `personState` is not
   updated. Each Auction probes the state for its seller. A seller absent from
   the savepoint produces no result and is not inserted into state.

The source uses a different operator UID in measure mode
(`nexmark-source-measure` instead of `nexmark-source`). This keeps the
build-phase source position and event limit from replacing the new source
configuration on restore. The Person extraction, Auction extraction, join,
and sink retain their UIDs so their compatible state can be restored. The
experiment runner uses Flink's `-n` option to allow the old source state to
remain unrestored.

## Command-line options

The job reads options with Flink's `ParameterTool`. These are the defaults in
`NexmarkQ3Job.java`, not necessarily the values used by an experiment runner.

| Option | Java variable; default | What it controls and where it is used |
| --- | --- | --- |
| `--events` | `numEvents`; `500000` | Maximum generated events across all event types. Passed to `NexmarkConfiguration` and `GeneratorConfig`. `0` is converted by `GeneratorConfig` to a very large limit, suitable for a run that the operator cancels. |
| `--source-keep-alive` | `isSourceKeepAlive`; `false` | Keeps a bounded source running after it generates `--events` records, allowing a savepoint to capture the complete Person-only build. Leave it false for a normal finite job. |
| `--working-set` | `workingSet`; `1000` | Assigned to `nexmarkConf.numActivePeople`. The modified `PersonGenerator.nextBase0PersonId` uses it when choosing seller IDs for Auctions. It changes the range of keys probed, not the number of Person records already present in a restored savepoint. Sellers are drawn from exactly `working-set` distinct keys: the first `working-set` Persons that exist, base ids `2 .. working-set+1` (the Persons the build generates start at base id 2; drawing from `[0, working-set)` named two sellers that never exist, so about 2/working-set of lookups missed). Upstream Nexmark's `PERSON_ID_LEAD` of 10 (which let auctions name sellers that did not exist yet) is not used. |
| `--parallelism` | `parallelism`; `1` | Sets the Flink environment and source parallelism and is copied to `numEventGenerators` for rate calculations. Keep the savepoint's parallelism and key-group compatibility in mind when restoring state. |
| `--person-proportion` | `personProp`; `10` | Relative share of generated Person events. Assigned to `nexmarkConf.personProportion`; these events build state in build mode and are discarded before the join in measure mode. |
| `--auction-proportion` | `auctionProp`; `4` | Relative share of Auction events. Assigned to `nexmarkConf.auctionProportion`; each generated Auction reaches the join and probes `personState`. |
| `--bid-proportion` | `bidProp`; `36` | Relative share of Bid events. Assigned to `nexmarkConf.bidProportion`. Bids consume source work but are filtered out of both join inputs. |
| `--hot-sellers-ratio` | `hotSellers`; `1` | Controls `AuctionGenerator`'s hot-seller branch. At `1`, that branch is never selected and seller IDs are drawn from the fixed active range. Values above `1` favor a smaller set of hot sellers, changing the lookup distribution; that branch derives IDs from generated Person history rather than the fixed active range. |
| `--person-avg-size` | `personAvgSize`; `200` | Target average generated Person size in bytes. Passed as `avgPersonByteSize`; the generator pads the Person's `extra` field, affecting state size per key. It is a target, not a guaranteed serialized state size. |
| `--compressible-extra` | `compressible`; `true` | Controls whether generated Person padding is compressible. Passed as `compressibleExtra`; it can affect the stored state's compression and cache footprint. |
| `--phase` | `phase`; default `build` | `build` or `measure` (case insensitive). Any other value is rejected at startup. Selects Person filtering, the source UID, and the job name. |
| `--tps` | `tps`; `0` | Target total events/second across all generators. `0` (default) emits at maximum speed; negative values are rejected. Achieved throughput can be lower. |
| `--key-dist` | `keyDist`; `uniform` | How sellers are drawn from the first `working-set` Persons that exist. `uniform` is the stock behavior and the worst case for caching. `zipf` makes a few keys receive most lookups, as in real workloads. Requires `--hot-sellers-ratio 1`. The key range is unchanged, so the same savepoint stays valid. |
| `--zipf-s` | `zipfS`; `0.99` | Zipf exponent for `--key-dist zipf`. Larger means more skew; `0.99` is the YCSB default. Must be positive. |
| `--savepoint-persons` | `savepointPersons`; `0` | Optional guard for `--phase measure`: the number of Persons in the restored savepoint. If `--working-set` exceeds it, the job fails at startup instead of silently dropping auctions for missing sellers. `0` disables the check. |

The default proportions `10:4:36` mean 20% Person, 8% Auction, and 72% Bid
events.


## Startup validation and metrics

The job rejects invalid arguments before submission: an unknown `--phase`, negative or
all-zero proportions, `--phase measure` with `--auction-proportion 0`, a negative `--tps`,
and (when `--savepoint-persons` is given) a working set larger than the savepoint. The
startup banner prints the expected Person count for a build run, and warns when
`--hot-sellers-ratio` is not 1.

**Key skew.** With `--key-dist zipf`, `--working-set` is the size of the key universe, not the
effective working set: the startup banner prints how many keys receive 50%, 90% and 99% of lookups,
and that hot set is far smaller. Hot keys are scattered across the id space (a bijective scramble of
rank to id), so they do not sit next to each other in the sorted SST files, which would flatter the
block cache. Compare a zipf run with a uniform run at the same `--working-set` to see how much of the
cost comes from the access pattern.

## Example invocation

The following illustrates a **measurement** run after a suitable build-phase
savepoint already exists. Replace the JAR and savepoint paths with those for
your environment. The JAR must contain this job class.

```bash
flink run -d -n -s /path/to/build-savepoint \
  -c com.github.nexmark.flink.NexmarkQ3Job /path/to/nexmark-async.jar \
  --phase measure --events 0 --working-set 1000000 --parallelism 4
```

The working-set sweep in `expr/working_set_vs_tp` restores one build-phase
savepoint for multiple measurements, varies `--working-set`, and reads the
join operator's throughput from Prometheus. Changing `--working-set` on a
restored job changes its lookup distribution; it does **not** rebuild the
savepoint or resize `personState`. For an experiment where the actual stored
state size must vary, create a corresponding build-phase savepoint for each
size.
